## 1. 必须回答的问题

1. raw 距离/时间是否与 `directionlite/v1/walking` 等价（含 `;UID` 绑路）。
2. 缺结果与零值如何与现有 unknown 对齐——**0 不得当覆盖**。
3. 矩阵没有 steps/path/实际端点：不能提供 ≤50m `endpoint_verified`，任何"伪设为 true"都必须被拒绝。
4. 最短距离选路与矩阵单值是否一致（报告已给出 950m/700s vs 1050m/600s 逻辑反例）。

## 2. 检查口径

输入为已提取的成对原始数值（不包含 AK、URL、请求头）；检查器零请求。

| 检查 | 规则 |
| --- | --- |
| 数值等价 | 以单点为基准：`|Δ| <= max(绝对容差, 相对容差 × 单点值)` |
| 距离 | 默认 50m 或 5%，两者取大 |
| 时间 | 默认 30s 或 10%，两者取大 |
| 零值/缺失 | 矩阵任一字段为 0 或缺失 → `matrix_unknown`，不是 match、不是覆盖 |
| 端点证据 | matrix 侧出现 `endpointVerified` 直接 `ValueError`；单点缺端点证据会标注"数值相同也不能证明业务等价" |
| 选路背离 | 矩阵距离更大且时间显著更短（超过距离绝对差与时间绝对差）→ `routeDivergence`，直接判不兼容 |
| UID 绑路 | `destinationUid` 原样记录并统计；UID 案例必须真实成对，不能靠坐标代替 |

容差是**待定值**：真实跨 API 误差尚未测得。默认值只用于链路验证，真实门禁阈值在成对基线完成后书面约定，本轮不虚构结论。

## 3. 输入 / 输出

输入 schema `matrix-contract-cases-v1`：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 用例标识 |
| `origin` / `destination` | 是 | `[lng, lat]` 或 `{lng, lat}` |
| `destinationUid` | 否 | 设施 UID |
| `single` | 否 | `{distance, duration, endpointVerified}` |
| `matrix` | 否 | `{distance, duration}`；**不允许** `endpointVerified` |
| `tolerances` | 否 | 覆盖默认容差 |

输出 schema `matrix-contract-review-v1`：`verdict`（`not_run` / `compatible` / `incompatible`）、`gateEligible`（仅 `label=paired-live` 为真）、`totals`（matches / mismatches / matrixUnknown / singleUnknown / routeDivergences / uidBoundCases / singleEndpointUnverified）与逐案例 `checks`。

合成示例结果：5 个案例、2 match、2 mismatch、1 zero-unknown、1 选路背离，`gateEligible=false`——符合预期，且明确不能当真实结论。

## 4. 真实成对测试协议（待授权）

1. **前置**：控制台确认 walking（`directionlite/v1/walking`）与矩阵（`/routematrix/v2/walking`）权限、每秒与日额度；预算单列，不与其他实验互借。
2. **点集预注册**：固定中心与少量 OD（含至少 1 个 UID 绑路案例），先冻结再调用，不按结果挑点。默认计划为 [frozen-plan.json](frozen-plan.json)；补 UID 后必须重新生成 `planHash`。
3. **调用**：`python -m tools.matrix_pair --mode live --plan <冻结计划> --output <cases>.json --collection-output <meta>.json --accept-quota --qps 3`。单点走现有 `LimitedProvider`/`RateGate`（响应后至少 1/QPS，最大在途 1）；矩阵按 OD 权重补齐到达节拍后一次 1→N 请求。临时失败最多重试一次，限流/配额/权限/参数错误立即停止后续发送。
4. **记录**：只留原始数值、reason、端点核验与耗时；不记录 AK、URL、请求头；`0`/缺失一律 unknown。collection 元数据记录单点与矩阵 HTTP 数、停止原因与计划哈希。
5. **禁止**：不把矩阵结果写入 reachable/coverage；不把 `endpoint_verified` 从矩阵推断；不用"只验证部分候选"换时间；不按 HTTP 次数声称省配额。
6. **产物**：`label=paired-live` 的 cases 与 collection 文件（拒绝覆盖），再跑契约检查器得到 review。三份文件都写入 stage-3 目录，全部通过才可能进入阶段四。

## 5. 门禁

- 全部可用的成对 OD：数值在约定容差内、无选路背离、零值/缺失按 unknown 处理、UID 案例可核验 → 才有资格进入阶段四设计。
- 任一不满足 → 不在数据上反复调容差；书面关闭矩阵替代，保留单点 Provider。
- 即使数值通过，也必须在阶段四另证业务正确性、失败率与 N=50/100 真实 wall-clock 收益，才谈正式实现。

## 6. 检查器不能证明的事

- 真实跨 API 误差与延迟（需要真实配对与分阶段计时）。
- 平台配额与到达节拍行为。
- 批次失败对健康 OD 的重试计费放大（报告已有诊断）。
- 任何"传输加速"的业务收益。

## 7. 复现

```text
# 1) 零请求：冻结计划
python -m tools.matrix_pair --mode plan --n 5 --output docs/performance/poi-distance/stage-3/frozen-plan.json
# 2) 授权后：真实成对收集（需 --accept-quota，qps 上限 3）
python -m tools.matrix_pair --mode live --plan <冻结计划> --output <cases>.json --collection-output <meta>.json --accept-quota --qps 3
# 3) 契约检查
python -m tools.matrix_contract --input <cases>.json --output <review>.json --label paired-live
python -m pytest tests/test_matrix_contract.py tests/test_matrix_pair.py -q
```

所有 `--output` 已存在时拒绝覆盖；只有 `label=paired-live` 能过门禁。
