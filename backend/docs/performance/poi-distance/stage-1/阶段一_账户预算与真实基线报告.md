## 3. 配额清单与出处

`quota-inventory.json` 与两次 live 输出的 `inventory.console` 生成时仍为 `not-read-from-console`（工具不联网读控制台）。2026-09-16 用户核验 walking 控制台值后写入 [console-inventory.json](console-inventory.json)，并可由 `load_console_inventory` / `quota_inventory(..., console=...)` 合并进新生成的输出：

| 控制台项 | 值 | 来源 |
| --- | --- | --- |
| walkingPermission / walkingPerSecond / walkingDaily | null（旧 AK 为 granted / 3 / 5000，已作废） | 2026-09-17 换新 AK，待重核 |
| matrixPermission / matrixOdPerSecond / matrixDaily | null（未核验） | 阶段三需单独核验 |

旧 AK 下本地 pacing 应 ≤3；换新 AK 后清单已清空（`consoleWalkingVerified=false`），核验前仍按保守 pacing。`.env` 中的 400 只是开发值。旧 AK 的真实请求消耗为 live v1+v2 共 60 次；新 AK 另做了两轮 QPS 试测（各 51 次），见 [QPS 试测报告](../qps-probe/探测报告_20260917.md)。

本地 `backend/.env` 当时为 `ANALYSIS_PROVIDER=synthetic`、`ANALYSIS_QPS=400`。该 400 是**本地 pacing 设置，不是控制台配额**；v2 输出显式写入：

```json
"provenance": {
  "liveProvider": "baidu/directionlite/v1/walking",
  "pacingQps": 3.0,
  "pacingQpsIsLocalOnly": true,
  "quotaSource": "local-env-not-console",
  "consoleCheckRequired": true
}
```

v1 的 `live-baseline.json` 未标注这一点，只在 inventory 里留下 synthetic/400，容易被误读为真实额度，v2 已修正并保留 v1 作对照。

独立限流器审计（只读）：

- `AnalysisManager.__init__` 在 `backend/app/analyses.py:169` 创建进程内共享 `RateGate(settings.analysis_qps)`，该进程全部任务共用这一把限流。
- `PoiRuntime.__init__` 在 `backend/app/poi/runtime.py:77` 使用 `gate or RateGate(self.config.qps if live else None)`；生产入口 `backend/tools/poi_collect.py:30` 不传 `gate`，因此 B1 采集有自己独立的 `RateGate`。
- 两者没有共享对象、没有跨进程协调；若同用一份 `.env` 的同一 AK，实际到达速率是两者之和。`quota_inventory` 的 `sharedAccountLimiter=false`、`crossProcessLimiter=false`、`b1JoinedFacilities=false` 与代码一致。

## 5. 与 v1 的对照及失败原因

| 配置 | pacing QPS（记录） | wallMean (s) | walking/轮 (s) | failures | maxInFlight |
| --- | --- | --- | --- | --- | --- |
| v1 `live-baseline.json` | 400（本地，未核实） | 3.826049 | 1.726602 / 0.840331 / 0.549360 | 1 / 2 / 3 | 1 |
| v2 `live-baseline-v2.json` | 3（本地，未核实） | 8.106526 | 3.473312 / 3.415833 / 4.918063 | 0 / 0 / 0 | 1 |

v1 的失败原因没有落盘（旧版只统计 `failures`），因此**不能**把它归因于限流；但可以观察到：同一组目的地、同一 Provider，在 400 pacing 下每轮递增出现 1/2/3 次失败，在 3 QPS 下三轮全部成功。这是"高本地 pacing 存在风险"的一致性信号，不是已证实的上游限流结论。v2 已修复原因采集，后续运行可直接给出 `no_result`、`rate_limit`、`endpoint_offset` 等分类。

也不得由 v1/v2 的耗时差宣称优化收益：两者 pacing 不同，且 v1 有失败被计入 wall-clock。

## 10. 复现

```text
python -m tools.stage_baseline --mode inventory
python -m tools.stage_baseline --mode inventory --console-inventory docs/performance/poi-distance/stage-1/console-inventory.json
python -m tools.stage_baseline --mode mock  --qps 3 --output <新文件>.json
python -m tools.stage_baseline --mode live  --n 10 --qps 3 --accept-quota --output <新文件>.json
python -m pytest tests/test_stage_ledger.py -q
```

`--console-inventory` 只读取人工核验文件，不联网；未提供时 `inventory.console` 保持 `not-read-from-console`。

live 模式：必须 `--accept-quota`；pacing 默认取 `ANALYSIS_QPS`，也可用 `--qps` 覆盖，但超过 `--live-max-qps`（默认 3）会直接拒绝；`--output` 已存在时拒绝覆盖，因此新结果必须写新路径。
